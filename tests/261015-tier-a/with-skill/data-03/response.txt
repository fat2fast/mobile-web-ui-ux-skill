## Phone presentation

**INFERRED from `src/main.jsx` and `src/style.css`:** The current ten-column table has a 1080px minimum width while the sidebar still takes 100px on narrow screens. Scrolling to compare status and total can separate those values from the order ID and selection control. This is a source-based diagnosis; the screen was not rendered.

Use a compact **comparison table in a full-width Orders area** on phones. Keep a persistent order ID and selection column at the start of the table, with Status and Total immediately beside them. Allow horizontal scrolling for Date, Items, Channel, City, and the row action; show that more columns are available. Keep column headings associated with values and preserve the existing detail route for the full record. This favors aligned status/total comparison across many selected orders. A stack of cards is a viable alternative for browsing individual orders, but makes cross-order comparison and bulk selection slower and less clear. The present full-width scrolling table is also viable for dense data, but loses row identity when scrolled.

Place Search, Status, and Sort above the results, with the active filter and a visible Reset control. Keep Export visible and make its scope explicit as **Export visible orders**, matching the current handler. In selection mode, show a selection count and a clear bulk-action control near the results, without covering rows or the mobile keyboard. Give each row an explicit checkbox labeled by order ID; provide a clear-selection route. State whether selection survives filtering: the current state retains selected IDs when they leave the visible list, so the count must represent *all selected orders*, including hidden ones, and users need a way to inspect or clear them before acting. Do not silently change selection scope. Preserve search, status filtering, ID/customer/date sorting, export, individual Follow-up, and order detail/Back behavior.

## Bulk-action safety

The current bulk handler accepts every selected ID, reports a local follow-up message, and clears the selection. The fixture has no authentication, authorization, status eligibility, server request, or persistence. **Do not infer permission from a status label** or disable action for Pending, Shipped, or Delivered based on this demo. For a real permitted bulk action, apply the product's actual server-side authorization and eligibility rule to the complete selected set; show the exact eligible IDs/count and action in a review step, make hidden filtered selections explicit, offer Cancel, and present any denied or changed records with a reason before submission. Confirm the operation's effect and reversibility from the real rule before deciding whether extra confirmation or undo is appropriate. Prevent duplicate submission while a real request is pending, then announce success or partial failure without erasing failed selections. The product owner must supply the real permission and eligibility policy; the fixture cannot establish it.
