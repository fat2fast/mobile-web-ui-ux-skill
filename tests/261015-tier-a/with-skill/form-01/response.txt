## Recommended mobile form

Use one column with visible labels in this order: Name, Email, Message, then an in-flow **Send message** button. Keep the form on one page; three fields do not warrant steps. Give Email an email input with email autocomplete and a suitable mobile keyboard, and make Message a multiline field. Keep labels visible while users type, allow paste, and leave enough space for the focused field and submit button when the keyboard opens.

For an invalid email, show a short, specific message directly under Email, such as “Enter an email address like name@example.com.” Identify the field visually and programmatically, and connect the message to it. After a failed submit, move focus to the first invalid field or an error summary that links to it. Keep Name, Email, and Message exactly as entered so users can correct only the address and submit again. Clear the error when the address becomes valid under the product's existing rules. Show a clear sending state and distinguish a server failure from an input error; on server failure, preserve all entries and offer retry. Show a confirmation only after submission succeeds.

**Decision and trade-off:** A single page with errors beside the relevant field makes recovery direct. A multi-step form could reduce what appears on screen, but adds navigation and risks losing context for only three fields. Avoid an error toast alone because it can disappear or sit away from Email. Optional typo suggestions should require the user's explicit choice and must not block an address that existing validation accepts. Do not add a stricter email or domain rule without a product requirement.

**Evidence and preservation:** The provided fixture is an order dashboard; its source has no contact form, email rule, or submit handler. The layout and recovery behavior above are recommendations for the stated scenario, not observations of an implemented form. Preserve any existing validation and submission contract, entered values, keyboard and zoom access, and desktop behavior when applying them.

**Verification to run after implementation:** On a phone with the on-screen keyboard, enter an invalid email and submit; confirm the inline error is announced and focus reaches it or Email without hiding it. Correct only Email and resubmit; confirm Name and Message remain, the error clears, and success appears only after a successful response. Repeat with an empty required field, a server failure, keyboard navigation, zoom, and a desktop viewport. These form checks were **NOT RUN** because the supplied fixture contains no contact form.
