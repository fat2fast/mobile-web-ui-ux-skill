## Mobile UX recommendation

The new product rule is explicit: Follow-up applies only to Pending and Shipped orders. Delivered orders remain visible in search, filters, the list, and details. The current fixture accepts all statuses in its row, detail, and bulk handlers (`src/main.jsx`), so the rule needs enforcement in every entry point, not just a visual change.

Keep the existing table and its selection controls for this scoped change. On a phone, place a clearly labeled bulk action with the selection summary where it remains discoverable without covering rows. Reuse the current styling and retain horizontal access to every column, sort, search, filters, export, and order details. A card rewrite would be a larger change and risks losing the table's scan and selection context.

For each selected set, calculate eligibility from the current order records, including selected rows hidden by a search or status filter. Show both the total selected and the eligible count beside the action. For example, with two Pending/Shipped orders and one Delivered order selected: **“3 selected · 2 eligible · 1 Delivered excluded”** and **“Follow-up eligible (2)”**. The action processes only the two eligible orders. Make the exclusion visible before activation, then announce a result such as “Follow-up recorded for 2 orders; 1 Delivered order was skipped” in the existing status region. Include order IDs or a way to review them if the selection can span filtered results. Clear the completed selection after reporting the result so stale selections do not imply a pending action. If every selected order is Delivered, disable the bulk action and keep a visible explanation, “Delivered orders cannot receive Follow-up.” Do not silently process or silently skip any selected record.

In each row and on the detail page, keep the order and its status visible. Pending and Shipped retain an actionable Follow-up control. For Delivered, replace that control with a readable “Follow-up unavailable for Delivered orders” explanation. Apply the same eligibility guard in the shared action logic so a stale screen or changed status cannot record an ineligible Follow-up. If a backend action exists outside this fixture, it must enforce the rule too; no backend is visible in the inspected files.

This keeps direct actions and bulk selection available while making the new rule legible. A viable alternative is disabling bulk Follow-up whenever any selected order is Delivered; that avoids partial processing but forces users to find and deselect ineligible records, which is especially awkward when filters hide part of the selection. The proposed eligible-only action makes the exact affected count and exclusions explicit.

**Evidence and checks:** INFERRED from `src/main.jsx` and `src/style.css`: the current action handlers have no status guard, the bulk handler uses every selected ID, and the table has a 1080px minimum width inside horizontal overflow. The proposed interaction has not been implemented or browser-tested. **NOT RUN:** On mobile widths, keyboard and desktop, verify mixed selection, all-Delivered selection, filter changes with hidden selected rows, row/detail actions, announcement text, focus, zoom, scrolling, and that Pending/Shipped actions still work. Also test a status change between selection and activation against the actual action boundary. These are recommended checks, not claimed results.
