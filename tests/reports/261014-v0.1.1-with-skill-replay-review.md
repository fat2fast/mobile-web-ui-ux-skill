# Review of the v0.1.1 with-skill replay

Date: 2026-10-14

Scope: six archived `tests/v0.1.1/with-skill/` responses, manifests, run metadata and transcripts; historical `tests/v.0.1.0/` outputs; current decision and verification contracts. This is a review of generated advice, not an implementation or a controlled A/B comparison. No fixture, skill, or response artifact was changed for this review.

## Executive decision

**PARTIAL improvement; NO-GO for a superiority or verified UX claim.** The replay removes the old explicit exclusion of Delivered orders, the old email submission block, the unsupported DATA-02 “Verified” statement, and the unconditional A11Y-01 conformance assertion. It does not establish that an implemented mobile experience is better. DATA-03 still prescribes unsupported eligibility and permission gates, FORM-01's sample fails to display its advertised typo suggestion and bypasses required non-email fields, and the archived runs are not isolated. DATA-02 is especially weak as an independent case: its transcript is the DATA-01 transcript with one more event.

The user decided to retain `v.0.1.0/no-skill` as the historical reference and replay only `with-skill` for these six cases. That is sufficient for a **targeted regression review of the skill's outputs**, provided the result is described as such. A fresh no-skill run is needed only for a new controlled comparison using the same protocol and runtime controls; an unchanged no-skill project alone does not make a new A/B result.

## Skill improvement direction

Keep the next skill change small and tied to the replay failures. The current contract already says to preserve existing business rules, keep typo suggestions optional, avoid untested conformance claims, and omit unsolicited implementation code (`references/decision-contract.md:17-19`, `references/decisions/forms.md`, `references/decisions/accessibility.md`, `SKILL.md:86`). The problem is that the replay did not consistently follow those instructions. First test whether a more prominent, concrete check changes the answer; do not duplicate the same rule across every reference or rewrite the architecture.

## Evaluation limits and next actions

1. **P0 — Repair replay provenance before treating v0.1.1 as a release gate.** Keep the current archive intact. Record DATA-02 as non-independent. For a new run, create a separate clean workspace and new agent conversation per case; expose only that case's prompt and fixture, verify the prompt appears in the transcript, and store the actual model/settings, budget, tool access, ambient instructions, workspace hash and timestamps. This follows `evals/comparison-protocol.md:7-11`. Definition of done: each case has its own first user request, non-overlapping transcript, matching prompt hash and reproducible manifest. No-skill may remain historical for targeted skill regression; rerun it under the same controls if making a new comparative win claim (`evals/comparison-protocol.md:19`).
2. **P0 — Hold business-rule changes.** In `references/decision-contract.md` and `references/decisions/actions.md`, keep the existing “inspect handler before adding eligibility” rule decisive; tighten wording only if further isolated output shows the same failure. Definition of done for the next DATA-03 replay: it preserves follow-up on Pending, Shipped **and Delivered** in the supplied fixture, and treats any new permission/status matrix as a product decision to validate, not an assumed rule. Do not implement a new gate solely from this advice.
3. **P1 — Correct the FORM-01 example before reuse.** The affected sample is `tests/v0.1.1/with-skill/form-01/response.txt:69,285-327`; any durable fix belongs in `references/decisions/forms.md` or a real runnable form fixture, not by rewriting archived output. Definition of done: valid `user@gmai.com` remains submittable and receives an optional suggestion; clicking suggestion changes only with user consent; empty Name, Email and Message are rejected with accessible recovery; uncommon/uppercase/plus-addressed emails remain accepted when syntactically valid.
4. **P1 — Remove unmeasured effect sizes from decision guidance.** Review `references/report-template.md`, `references/evidence-template.md` and `references/verification-criteria.md` only if an isolated replay still produces a claim such as DATA-02's 40–60% reduction. Definition of done: measured percentages have a named before/after artifact and method; otherwise the response gives a qualitative hypothesis and `NOT RUN`.
5. **P1 — Build evidence on runnable applications.** A proposal is not a UX improvement. Use an appropriate order-dashboard and contact-form fixture, capture baseline and changed screenshots/task results at phone widths and a desktop width, run behavior and accessibility checks, and archive the commands, environment and outcomes under `evals/results/`. Definition of done: the required primary task works on the changed UI, preserved functions and desktop remain functional, and actual failures/untested states are explicit (`references/verification-criteria.md:28-42`).
6. **P2 — Improve answer calibration and advice scope.** In the next replay, separate source inspection (`INFERRED`), metadata integrity, executed checks (`PASS`/`FAIL`) and proposed checks (`NOT RUN`); avoid precise layout and WCAG outcomes without measurements. Check that an advice request returns a concise decision and verification plan without unsolicited implementation code. Update skill text only for recurring failures evidenced by isolated runs.
