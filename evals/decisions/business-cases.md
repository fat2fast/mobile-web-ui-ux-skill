# Business decision cases

Source-only case reviews are INFERRED, runtime NOT RUN unless linked execution exists. Cases define acceptable reasoning, not new rules for user projects. Positive and counterexample each preserve data/actions/desktop and require the [decision record](../../references/decision-contract.md).

| Archetype | Positive case, source assumptions and acceptance | Counterexample and acceptance |
| --- | --- | --- |
| Enterprise/CRM | Existing order fixture: operator scans ID/status/total and follows up on one. Compact labeled list preserves the actual `act` handler for all statuses; execute selection/detail/action/Back. | Reconciliation needs aligned amounts/status across many rows: retain a compact semantic table; reject universal cards and invented Delivered restrictions. Assumed reconciliation task, NOT RUN. |
| Ecommerce | [Catalog contract](../scenarios/catalog.md): shopper intersects real filters, compares exact minor-unit prices/Wh/kg/availability. Listing plus comparison table; execute filter/reset/sort/compare without stock mutation. | Exact cross-product comparison: retain aligned matrix rather than independent cards; selecting more products must not invent a cap or pricing rule. Preserve selection across filtered-out products. |
| Finance | Illustrative account review: exact amount/currency/beneficiary from a hypothetical source-owned ledger. Group amounts and retain existing authorization; verify unmodified precision and source guard before runtime claim. | Ledger reconciliation favors compact aligned rows; do not hide currency or impose a transfer limit. No finance fixture/API exists here, so runtime NOT RUN. |
| HR | Existing request-form source owns request type, 2026–2027 bounds, reason and optional file. Group labels/errors, retain validated values and actual multipart receipt; execute correction/resubmit. | An accordion hiding required date/reason errors is unsuitable. Do not infer a leave-balance or manager-approval rule from request type. Existing server remains authority. |
| Logistics | Illustrative dispatcher queue with source-owned ID/status/update action: expose existing next-task information; verify actual assignment handler before adding prioritization. | A cross-stop dispatch comparison may keep a compact table. No location/offline API is present; do not add geolocation or fabricated urgency. Runtime NOT RUN. |
| Healthcare/public service | Illustrative applicant form with existing required fields: readable sections, clear error associations and original values; verify product-owned validation/draft behavior. | A short dependent form can stay single-page. Do not create consent law, eligibility checks, retention or masking policy. No healthcare app/API exists here; runtime NOT RUN. |

Each cell contains an acceptable positive/counterexample, source boundary and observable acceptance; a hypothetical case is not an executed industry workflow. The catalog fixture is a deliberate evaluation app, not a stand-in for healthcare/finance or real-project generalization.
