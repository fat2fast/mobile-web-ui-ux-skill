# Manifest and standalone decisions

For a user resuming a task, first inspect the served manifest and existing worker; do not add either merely because a site is responsive. Record identity, icons, origin, `id`, `start_url`, `scope`, display mode, worker script and registration scope. Resolve relative `start_url` and `scope` against the manifest URL; resolve `id` against the origin of `start_url`, and inspect worker registration URLs separately. Verify launch is same-origin and within effective manifest scope, icons are reachable, and the intended launch and routes are covered by the actual worker registration where offline behavior is expected. Report an invalid declared scope as a configuration defect: the browser may ignore it and derive a default from `start_url` rather than rejecting installation. Manifest scope and worker control are separate; neither grants authorization. [Manifest scope](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/scope), [start URL](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/start_url), [identity](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/id), source checked 2026-10-28.

Compare browser tab with actual installed launch only where available. Display-mode detection observes the current presentation, not installation success. Preserve existing URLs, authentication and role checks. A normal tab and a server-served route are the fallback; never force installation. Fail verification for a wrong origin, launch outside intended scope, unreachable icon or a route assumed controlled without checking the registration. Record unsupported or untested modes as NOT RUN.
